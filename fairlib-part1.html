Part 1 — fairlib basics

What a language model is

A large language model (LLM) is a next-token predictor wrapped in a conversation format. One mechanism, repeated:

Step 0 / 5

From language to tokens

The model never sees words. Text is chopped into tokens, and each token becomes a vector — a long list of learned numbers:

  • Words become tokens; tokens become vectors. Common words survive whole; rare words split into pieces ("annoyingly" → annoying + ly).
  • Qwen2.5: a learned vocabulary of 151,643 tokens.
  • Each token ID selects one row of a learned lookup table — for Qwen2.5-7B, a vector of 3,584 numbers. From here on the model sees only vectors.
  • Everything the model does is math on those vectors — and all of it exists to produce one thing: a probability distribution over every token it knows, from which the next token is picked.

Training: tuning a mountain of matrices

A forward pass is almost entirely matrix multiplication. Training means nudging the numbers in those matrices — trillions of times — until next-token prediction stops being wrong:

  • Llama 3.1 405B: 405 billion parameters, tuned over ~15 trillion training tokens on more than 16,000 H100 graphics processing units (GPUs), ≈3.8×1025 floating-point operations (FLOPs) of training compute.
  • The trend (Epoch AI): frontier training compute grows ~5× per year; the largest single runs are projected to need 4–16 gigawatts by 2030 — one nuclear reactor powers about a gigawatt, roughly 830,000 homes.

This is why the data centers are going up. The buildings, the power contracts, the cooling — all of it exists to run this loop at that scale.

Stochastic by design

  • A distribution, not an answer. Every pass scores the whole vocabulary; the output is a weighted dice roll over the top of that list. The randomness is real — but it comes with knobs you can tune:
  • Temperature reshapes the dice. It divides the raw scores before softmax — low temperature sharpens the distribution toward the favorite (repeatable), high temperature flattens it (creative, erratic).
  • Top-p trims the tail. Keep only the smallest set of tokens covering p of the probability mass, then roll among those.
  • Greedy decoding — always take the top token — is deterministic. But chat systems sample by default: same prompt, same model, different tokens. By design, not by bug.

Every demo in this talk is a real run of Qwen2.5-7B on local hardware. Reruns can and do produce different output — that is the stochastic component doing what it does. The entire discipline you are about to learn is engineering reliable systems on top of a component that is random by design.

The confident liar

Ask the model for arithmetic:

a, b = 48193, 90271
guess = llm.invoke([Message(role="user", content=f"What is {a} * {b}? Reply with the number only.")])
print("MODEL SAYS: ", guess.content)
print("PYTHON SAYS:", a * b)

MODEL SAYS: a fluent, number-shaped guess — different every run, wrong every run.

PYTHON SAYS: 4,350,430,303 — every run.

Same story for the current temperature in Colorado Springs or the Bitcoin price: a specific, plausible figure it cannot possibly know — in the same confident tone. Fluency is not accuracy, and nothing in the reply tells you which one you got.

It's just input / output

Strip the chat interface away and the entire contract is one pure function:

Limit 1 — stateless. Nothing survives between calls. There is no session and no "it remembers me".

Limit 2 — confidently wrong. It predicts text; it does not compute, look up, or verify.

Everything in fairlib — prompts, agents, tools, memory — is scaffolding around these two limits.

Serving it locally — the adapter seam

llm = HuggingFaceAdapter(MODEL_NAME, max_new_tokens=256)  # in-process, your GPU
# llm = OllamaAdapter(...)   # local server  — same interface, same code
# llm = OpenAIAdapter(...)   # hosted        — the one-line swap

Select the model for the mission. The interface makes models interchangeable — capability is not. A model that chats fluently may still fail at planning or tool use, so test candidate models against your actual use case and choose the smallest one that handles it reliably.

The Message class

Message(role, content, tool_calls=None, name=None, tool_call_id=None,
        metadata={}, importance="normal")
  • role — who is speaking: system (standing orders from the operator), user (the human turn), assistant (the model's own words), tool (machine results from tools).
  • content — the text of the turn. The model reads this and the role that frames it — nothing else.
  • tool_calls / tool_call_id / name — structured tool-request bookkeeping; the agent loop fills these in for you.
  • metadata / importance — your annotations; importance="pinned" is a memory-survival contract Part 2 builds on.

The whole API in two lines

reply = llm.invoke(
    [Message(role="user", content="In two sentences, why do aircraft take off into the wind?")]
)
print(reply.content)
  • Message(role=..., content=...) — one turn of conversation, as a typed object.
  • llm.invoke([...]) — a list of messages in, exactly one assistant Message out.
  • That is the entire surface. Everything else in fairlib is built on top of this one call.

Run 1 — reply.content is just a string: "Aircraft take off into the wind because a headwind increases airflow over the wings, producing lift at a lower ground speed. That shortens the takeoff roll and steepens the climb."

Run 2 — the very same call: "Taking off into the wind raises the airspeed the wings feel, so the aircraft lifts off sooner and clears obstacles more easily." — same facts, different words. The dice roll, live.

What invoke() does

  • The chat template stitches your typed messages into one token sequence, with special tokens marking each role boundary — this is where "roles" physically live.
  • The generation loop is exactly the next-token cycle you stepped through at the start of the hour — run once per output token until a stop token lands.

One call = one turn, and nothing is stored anywhere in that pipeline. Whatever history you want the model to see must be inside the list you pass. Watch what that means, live, in three moves →

The scenario: will it remember Viper-2?

You are building a comms assistant for the ops net. A flight checks in; protocol says acknowledge and carry on. A few minutes later, the desk needs the assistant to recall who it is talking to.

  • Move 1 — contact. The pilot checks in with a callsign; the assistant acknowledges.
  • Move 2 — the test. We ask the very same model object: what is my callsign?
  • Move 3 — the fix. We ask again — this time replaying the conversation into the call.

Before each move, commit to a prediction: what will the model say? You just learned it is a stateless pure function — hold that idea in your head and call the outcome before it appears.

Viper-2, move 1 — contact

intro = Message(role="user", content="My callsign is Viper-2. Acknowledge in three words.")

ack = llm.invoke([intro])
print("ACK:", ack.content)

ACK: "Viper-2, acknowledged, standing by."

  • The model used the callsign because the callsign was in the list it just read. Nothing more mysterious than that.
  • Keep your eye on the llm object — the same instance answers the next slide.

Viper-2, move 2 — amnesia

intro = Message(role="user", content="My callsign is Viper-2. Acknowledge in three words.")
# …the same llm instance that just acknowledged Viper-2:

amnesia = llm.invoke([Message(role="user", content="What is my callsign?")])
print("WITHOUT HISTORY:", amnesia.content)

WITHOUT HISTORY: "I do not see a callsign in this conversation — could you provide it?"

  • Seconds after acknowledging, the same object has no idea. No state survived the call.
  • There is no session, no login, no "it remembers me". The pure function got a one-message list, so one message is the entire world it answered from.

Viper-2, move 3 — recall, by replay

intro = Message(role="user", content="My callsign is Viper-2. Acknowledge in three words.")

recall = llm.invoke([intro,                                       # the original turn
                     Message(role="assistant", content=ack.content),  # its own reply
                     Message(role="user", content="What is my callsign?")])
print("WITH HISTORY:", recall.content)

WITH HISTORY: "Your callsign is Viper-2."

History is not stored by the model — it is re-sent by you, every turn. And this is still ONE call: several messages in a single invoke is one turn. Automating this replay is the first thing agent memory will do for you.

Part 1 · Section B

Prompts that hold

Typed parts in, typed records out.

The scenario: an ops desk, listening to the radio

A crackle on the frequency. Amid a busy shift, the desk hears this:

"uh center, this is REEF 41, single F-16, we're showing twenty-five hundred
pounds of fuel, call it three and a half hours remaining, three souls on
board - correction, two souls on board - negative emergency at this time,
requesting flight following to Bravo sector."
  • Your program is the ops-desk formatter: turn that transmission into a clean, typed record the rest of the system can trust.
  • The crew corrected themselves mid-call. The dispatcher is juggling six other flights. Details slip — and details here are lives and fuel.
  • The mission for this section: a prompt that holds — same messy radio traffic in, same structured record out, every run — and code that catches what the humans miss.

Prose is for humans

First, the naive approach — "Summarize this radio report:" — three real runs of Qwen2.5-7B on the same transmission (abridged):

Run 1: "The radio report from REEF 41, a single F-16 aircraft, indicates the following: - Current fuel level: 2500 pounds - Estimated remaining flight time: approximately 3.5 hours …" — a bullet list.

Run 2: "The radio report indicates that REEF 41, which is a single F-16 aircraft, has approximately 2,500 pounds of fuel remaining, equivalent to about three and a half hours of flight time. …" — now a paragraph.

Run 3: "… This information is crucial for air traffic control to ensure safe navigation and monitoring of the aircraft." — bullets again, closing with unsolicited commentary.

Wording, order, even the format — all shift run to run. There is no slice, split, or regex that parses a reply that restructures itself every call.

Where this section lands: schema + validation → FlightRecord(callsign="REEF 41", fuel_pounds=2500, souls_on_board=2, …) — the same object, every run.

PromptBuilder — the whole class

fairlib composes system prompts from typed parts held by one builder object — never from a hand-glued string:

  • Each part is a typed object (RoleDefinition, FormatInstruction, Example) — you compose them; the builder renders them into labeled sections.
  • Composed parts do not drift the way one hand-edited prompt string does — and clone() gives you a safe copy to vary per agent.

The typed parts, in code

builder = PromptBuilder()
builder.role_definition = RoleDefinition(
    "You are an operations desk formatter. You convert messy aircrew "
    "radio reports into precise structured records. You never invent "
    "information that is not in the report."
)
builder.format_instructions.append(FormatInstruction(
    "Reply with ONLY a JSON object matching the schema you are given. "
    "If the crew corrects themselves mid-report, record the corrected value."
))

Why do we need a role at all? The model sees one long token stream — it has no channels, no permissions, no speaker labels of its own. Roles are the frame it was trained on: text marked system is treated as standing orders, so the same question under a "terse briefing officer" versus a "patient flight instructor" system message comes back in two different voices. fairlib places your text in the right role for you — the key is understanding what each role signals to the model, and designing your prompts around it.

What the model receives

print(builder.build_system_prompt_string()) — the parts, rendered into labeled sections (output abridged):

## Role
You are an operations desk formatter. You convert messy aircrew
radio reports into precise structured records. You never invent
information that is not in the report.

## Format instructions
Reply with ONLY a JSON object matching the schema you are given.
If the crew corrects themselves mid-report, record the corrected
value.
  • This exact string is sent as the system message — the standing orders slot from the Message-class slide.
  • Stable order, labeled sections: when a prompt misbehaves, you can point at the part that failed and fix that one object.

Pydantic Overview

Pydantic is a library for defining data shapes as Python classes and validating raw data against them. One class buys both halves of a contract:

class FuelCheck(BaseModel):
    callsign: str
    fuel_pounds: float = Field(ge=0, description="Pounds remaining; never negative")

FuelCheck.model_json_schema()      # → a JSON schema you can SHOW the model
FuelCheck.model_validate_json(raw) # → a typed object, or a ValidationError

{"callsign": "REEF 41", "fuel_pounds": 2500}
→ FuelCheck(callsign="REEF 41", fuel_pounds=2500.0) — a real object, fields typed and checked.

{"callsign": "REEF 41", "fuel_pounds": "plenty"}
→ ValidationError naming the exact field and rule it broke.

Schema + validation is the power move: the schema tells the model what shape to produce; the validator refuses everything else. You never parse model prose by hand — you accept typed objects or reject with evidence.

The validate-and-retry loop — recovery, not hope

for attempt in range(1, 4):
    raw = llm.invoke(messages).content.strip()
    try:
        record = FlightRecord.model_validate_json(raw)
        break                                    # VALID — typed object in hand
    except ValidationError as exc:
        # The failed reply and the validator's complaint join the
        # conversation, so the next attempt sees its own mistake.
        messages.append(Message(role="assistant", content=raw))
        messages.append(Message(role="user",
            content=f"That was not valid. Fix these problems and reply "
                    f"with ONLY the corrected JSON object:\n{exc}"))

Question for the room: tools like Claude Code generate code that fails on the first try all the time — yet they ship working software. How?

They read the error and repair. This loop is that same discipline: the model WILL hand you malformed output routinely, and recovery — feeding the failure back as evidence — is what turns a flaky component into a dependable one.

Small local models routinely fail attempt 1 — a markdown fence, a string where a number belongs. That is not the demo misbehaving; that is why this loop exists.

The model extracts; your code decides

The loop hands back a typed record of the REEF 41 call — and now deterministic code takes over:

record                    # FlightRecord(callsign="REEF 41", aircraft_type="F-16",
                          #   souls_on_board=2, fuel_pounds=2500.0,
                          #   crew_estimated_fuel_hours=3.5, emergency=False)

def assess_fuel_state(record: FlightRecord) -> str:
    actual_hours = record.fuel_pounds / BURN_RATE_LB_PER_HOUR   # 2500/2000 = 1.25
    if actual_hours < RESERVE_HOURS and not record.emergency:   # 1.25 < 1.50
        return "FUEL EMERGENCY - endurance below reserve, none declared."
    return "within reserve"
  • The crew estimated 3.5 hours. The arithmetic on the extracted fields says 1.25 — below the 1.5-hour reserve. The desk that was "just listening to radio traffic" catches the dispatcher's miss.
  • The model's only job was extraction into FlightRecord. Plain Python, in a plain method you can unit-test, made the life-safety call.

Division of labor: the model turns mess into typed data; deterministic code makes the decisions. Keep it that way in your capstone.

Part 1 · Section C

Your first agent

A planner, five components, one loop — and a redemption.

An agent is a loop, not a model

The five constructor arguments of SimpleAgent — each an interface in fairlib.core.interfaces.

You configure the components; fairlib runs the Thought → Action → Observation loop. Swap any part and the loop never knows the difference.

One composition root

tools = ToolRegistry()
tools.register_tool(SafeCalculatorTool())

planner = SimpleReActPlanner(llm, tools)
planner.prompt_builder.role_definition = RoleDefinition(
    "You are a precise operations assistant. Use your tools for any "
    "arithmetic instead of computing in your head."
)
planner.prompt_builder.examples.append(Example(
    "User: What is 12 * 31?\n"
    "Thought: Arithmetic goes to the calculator.\n"
    "Action:\ntool_name: safe_calculator\ntool_input: 12 * 31"
))

agent = SimpleAgent(
    llm=llm, planner=planner,
    tool_executor=ToolExecutor(tools),
    memory=WorkingMemory(),
    max_steps=6,
)
  • The appended Example is one worked turn showing the exact tool-call syntax — observed to be the single most effective reliability trick for small local models, which mangle the format without one.
  • This assembly is the composition root — the one place all the parts meet. Every capstone template starts from exactly this shape (build_agent()).

The planner: teaching the model to act

  • A planner turns the conversation so far into one of two typed outcomes: a final answer, or a tool request. It writes the reasoning rules into the prompt, and it parses the model's reply back into typed objects.
  • The reasoning pattern is ReAct — Reason + Act: Thought (reason about the next move) → Action (request a tool) → Observation (see the result) → repeat until it can answer.

What the model is trained to write back — SimpleReActPlanner's keyword format:

Thought: This is arithmetic. I should not guess - the calculator tool exists.
Action:
tool_name: safe_calculator
tool_input: 27 * 43
  • The planner parses that text into a typed Action — parsing and format discipline are its job, not yours.
  • Sibling planners speak other dialects — ReActPlanner uses a JSON body ({"thought": …, "tool_name": …, "tool_input": …}) — but the keyword format is the most robust on small local models, so it is the one we teach.

The redemption run

The same multiplication the raw model flubbed — now through the agent. Read the loop, not just the answer:

Task — await agent.arun("What is 48193 * 90271?")

Thought — "Arithmetic goes to the calculator."  Action — tool_name: safe_calculator · tool_input: 48193 * 90271

Execution — ToolExecutor validates the arguments against the schema gate, then runs the tool body: deterministic Python, no model involved

Observation — 4350430303 (deterministic — Python computed it)

AGENT SAYS 4,350,430,303 — PYTHON SAYS 4,350,430,303. A match, every run.

Part 1 · Section D

Tools are power

Tools are the hands: they give a language model the power to act on the world —
so declare the contract once, and let the framework enforce it everywhere.

A tool starts with its input contract

Scenario: an airfield ops assistant that resolves reported winds into runway components. The contract comes first — a Pydantic class:

class WindComponentInput(BaseModel):
    """Runway heading and wind, for a headwind/crosswind breakdown."""

    runway_heading_deg: int = Field(ge=0, le=360,
        description="Runway magnetic heading in degrees, e.g. 350 for runway 35.")
    wind_dir_deg: int = Field(ge=0, le=360,
        description="Direction the wind is blowing FROM, in degrees.")
    wind_speed_kt: float = Field(ge=0,
        description="Wind speed in knots; zero or greater.")
  • ge / le are validated bounds — "greater/less than or equal". A call outside them is rejected before your code runs.
  • The description strings are model-facing documentation — they will be rendered into the tool catalog verbatim. Write them for the model, not for yourself.

Anatomy of a tool — four declarations, one body

class RunwayWindComponentTool(AbstractTool):
    name = "runway_wind_components"
    description = ("Compute the headwind and crosswind components for a "
                   "runway heading and a reported wind. Do not estimate "
                   "the trigonometry yourself.")      # the ad the model reads
    input_schema = WindComponentInput   # the contract from the last slide
    output_schema = TextResult          # what callers get back
    side_effect = SideEffect.READ_ONLY  # ONE declared side effect per tool
    async def acall(self, tool_input: WindComponentInput) -> ToolOutput:
        angle = math.radians(tool_input.wind_dir_deg - tool_input.runway_heading_deg)
        headwind = tool_input.wind_speed_kt * math.cos(angle)
        ...
Step 0 / 4

One schema, three guarantees

The model-facing catalog, concretely — the entry compiled from WindComponentInput that the model reads in its system prompt (abridged):

runway_wind_components: Compute the headwind and crosswind components…
  runway_heading_deg (integer, 0-360): Runway magnetic heading in degrees…
  wind_speed_kt (number, >= 0): Wind speed in knots; zero or greater.

You never write prompt text for a tool, and you never parse a tool argument by hand. Generated from one source, the docs and the validation cannot drift.

One turn, end to end

The wind tool, registered and handed to the agent — one real run of Qwen2.5-7B, exactly as show_agent_mind(agent) prints it from working memory:

USER — "We are landing on runway 35, heading 350. Tower reports wind 020 at 18 knots. What are the headwind and crosswind components?"

THOUGHT — "We need to calculate the headwind and crosswind components for landing on runway 35 with the given wind direction and speed." — the model routes the question to a tool instead of guessing the trigonometry.

ACTION — tool_name: runway_wind_components
tool_input: {"runway_heading_deg": 350, "wind_dir_deg": 20, "wind_speed_kt": 18.0} — a JSON object using the schema's exact field names, learned from the generated catalog, never from hand-written prompt text.

OBSERVATION — "Runway heading 350, wind 020 at 18 kt: 15.6 kt headwind, 9.0 kt crosswind from the right." — the deterministic string acall returned. Every number in the answer traces back to it, not to the model.

AGENT: "Runway 35 has a 15.6 knot headwind and a 9.0 knot crosswind from the right." — plain radio phrasing, exactly what the FormatInstruction demanded.

Part 1 · Section E

Memory that survives

Forget by design — and know exactly what you lost.

The ring buffer forgets — blindly, by design

Scenario: the Falcon Telescope duty shift. Early in the evening, maintenance calls in: the dome crane is red-tagged — a lockout order: unsafe, do not operate until cleared. That order MUST survive the shift.

ring = WorkingMemory(max_size=6)          # keeps the 6 newest messages
for i in range(1, 10):
    ring.add_message(Message(role="user", content=f"log entry {i}"))

Later that night: "Can we rotate the dome to track a target in the west?" The red tag is gone from memory — the agent approves the rotation with total confidence. The naive strategy fails in the worst possible way.

Making orders survive — pinning them through summary compression — is deterministic-code territory, and it opens the memory chapter of Part 2.

Memory is a class — so reach for a better one

Appending to a bounded list is not a memory strategy. In fairlib, memory is an interface (AbstractMemory: add_message, get_history, …) — and the framework ships smarter implementations:

memory = SummarizingMemory(
    llm=llm,                     # uses the model itself to write summaries
    max_history_length=10,       # when history grows past this…
    messages_to_keep_at_end=4,   # …keep the newest verbatim,
)                                # and FOLD the middle into a summary
  • Compress, do not delete. The first message and the newest messages survive verbatim; the routine middle becomes a model-written summary. The shift stays coherent without the context window growing forever.
  • Same interface, drop-in swap. Hand it to the SimpleAgent composition root in place of WorkingMemory — the loop never knows the difference.
  • Or build your own. WorkingMemory, SummarizingMemory, and LongTermMemory ship today; a memory class tuned to your capstone's use case is a normal, expected thing to implement against AbstractMemory.

And the red tag? Summaries compress — an order's exact wording can still blur away. Making specific messages survive verbatim is where Part 2 picks up the story.

Retrieval-Augmented Generation (RAG), in four moves

  • 1. Embed — each document chunk becomes a vector of numbers that encodes its meaning, computed by a small dedicated embedding model (not the chat model).
  • 2. Store — FaissVectorStore keeps those vectors in a similarity index that persists to disk; ingest once, query for the life of the project.
  • 3. Retrieve — "wind limit for opening the dome" surfaces the right manual section by meaning, sharing almost no exact words with it. Pure vector math — this works before any chat model is involved.
  • 4. Ground — wrapped as KnowledgeBaseQueryTool, lookup becomes a choice the agent makes — and its answer cites the 25-knot limit because it read it, not because it guessed it.

Two memories, one project

Continuity — WorkingMemory (and Part 2's pinned, summarizing upgrade)

Fights the finite context window. Keeps this conversation coherent across a whole shift.

Capstone smell test: "the agent forgot what the user said ten minutes ago" → continuity problem.

Knowledge — LongTermMemory + retrieval-as-a-tool

Fights answering from training data. Grounds answers in your documents, with cited sources.

Capstone smell test: "the agent invented a regulation that is not in our manual" → knowledge problem.

Most real capstones need both at once. And one model instance can serve the whole system — answering the duty officer while also writing summaries — precisely because the model is stateless: it is still the same pure text-in / text-out function we started the hour with.

Takeaways

1An LLM is a stateless next-token predictor — tokens in, a probability distribution out, a dice roll to pick. That is why it is fluent even when wrong, and why agents exist.

2An agent is a loop, not a model. Planner decides, executor acts, memory remembers, adapter speaks to the model.

3The model is a swappable part, and serving is yours to choose — HuggingFace in-process, Ollama local server, or hosted, in one line.

4Tools are typed contracts. One schema generates the docs, validates every call before execution, and teaches the model to self-correct.

5Memory is two stores with two jobs — a bounded working ring for continuity, retrieval that cites its sources for knowledge. Making orders survive is Part 2's opening act.
